# Présentation du code principal (main.c)

## 1) Construction du code

### 1.1) Structure générale et organisation

Le fichier `main.c` constitue le cœur du jeu "Gros Nounours 2D" et centralise toute la logique principale de l'application. Il est organisé en sections clairement délimitées par des commentaires de séparation, comme le montre l'en-tête du fichier : `// ============================================================================`. Le code utilise la bibliothèque Raylib pour le rendu graphique et l'audio, ainsi que plusieurs modules de minijeux intégrés via des includes spécifiques : `#include "minigames/pousse_pousse/pousse_pousse.h"`, `#include "minigames/traffic/traffic.h"`, etc. La structure suit une approche modulaire avec des fonctions statiques pour encapsuler les fonctionnalités, évitant ainsi la pollution de l'espace de noms global. L'architecture principale repose sur une machine à états finis (FSM) gérée par l'énumération `GameState` qui définit les différents écrans du jeu : `STATE_TITLE`, `STATE_HUB`, `STATE_ZONE_JARDIN`, `STATE_SHOP`, `STATE_MINIJEU`, etc. Cette organisation permet une séparation claire des responsabilités et facilite la maintenance du code.

### 1.2) Types et structures de données

Le code définit plusieurs types personnalisés pour structurer les données du jeu. L'énumération `GameState` (lignes 28-38) représente les différents états possibles du jeu, tandis que `ZoneId` (lignes 41-48) identifie les zones géographiques du monde virtuel. La structure principale `Game` (lignes 74-148) centralise toutes les données du jeu, incluant l'état actuel, la progression, les textures, les positions des éléments UI, et les données de la boutique. Pour gérer l'adaptabilité à différentes résolutions d'écran, le code utilise des structures de positionnement relatif : `RectRatios` (lignes 59-64) stocke les positions en pourcentage avec `float left, top, width, height`, et `BearLayout` (lignes 67-71) gère spécifiquement la position du nounours avec `float left, top, heightRatio`. Cette approche permet au jeu de s'adapter automatiquement à différentes tailles de fenêtre sans recalculer manuellement les coordonnées absolues.

### 1.3) Gestion des états et de la navigation

Le système de navigation entre les écrans est géré par une machine à états implémentée dans la fonction `main()` via un `switch` sur `g.state` (lignes 1106-1267). Chaque état possède sa propre logique de mise à jour et d'affichage, comme illustré par le cas `STATE_HUB` (lignes 1110-1152) qui détecte les clics sur les portails de zones et la boutique. La conversion entre zones et états est assurée par la fonction `zoneToState()` (lignes 927-935) qui mappe les identifiants de zone vers leurs états correspondants. La transition vers un minijeu s'effectue via `prepareMinigameSession()` (lignes 276-289) qui initialise l'interface `MinigameAPI` et change l'état vers `STATE_MINIJEU`. La finalisation d'un minijeu utilise `finalizeMinigame()` (lignes 292-311) qui marque la zone comme complétée, nettoie les ressources, et retourne au hub. Cette architecture permet une gestion claire des transitions entre les différents écrans du jeu.

### 1.4) Système de rendu et affichage

Le système d'affichage est organisé en fonctions spécialisées pour chaque élément graphique. La fonction `drawMenuBackground()` (lignes 546-563) gère le fond du menu principal et change dynamiquement l'image affichée selon le portail survolé : `if (g->hoveredPortal >= 0 && g->hoveredPortal < ZONE_COUNT && g->hasZoneBackground[g->hoveredPortal])`. Le rendu du nounours est assuré par `drawBearCloseup()` (lignes 566-591) qui sélectionne la texture appropriée selon la tenue actuelle : `if (g->currentBearOutfit >= 0 && g->currentBearOutfit < 5 && g->hasBearOutfit[g->currentBearOutfit])`. Les informations de progression sont affichées via `drawMinigameStatusTable()` (lignes 594-626) qui dessine un tableau avec l'état de chaque minijeu, utilisant des couleurs conditionnelles : `Color statusColor = g->progress[i].completed ? (Color){ 120, 230, 140, 255 } : (Color){ 255, 210, 120, 255 }`. Le compteur de pièces est rendu par `drawCoinCounter()` (lignes 629-648) qui affiche un rectangle arrondi en haut à droite avec le nombre de pièces collectées. Toutes ces fonctions sont appelées dans la section d'affichage de la boucle principale selon l'état actuel du jeu.

### 1.5) Gestion des ressources et configuration

Le chargement des ressources utilise une fonction utilitaire `loadTextureIfAvailable()` (lignes 249-266) qui vérifie l'existence du fichier avant de charger la texture : `if (!FileExists(path)) { return tex; }`. Cette approche permet au jeu de fonctionner même si certaines ressources sont manquantes. Le système de configuration utilise un fichier INI (`config/menu_layout.ini`) pour sauvegarder les positions des éléments UI. La fonction `loadMenuLayout()` (lignes 362-407) lit ce fichier ligne par ligne et parse les positions avec `sscanf()` : `if (sscanf(line, "portal_%63[^=]=%f,%f,%f,%f", key, &left, &top, &width, &height) == 5)`. La sauvegarde est effectuée par `saveMenuLayout()` (lignes 410-433) qui écrit les positions au format `portal_jardin=0.065,0.25,0.11,0.30`. Le mode debug (activé par F2) permet de déplacer visuellement les éléments via `handleDebugDragging()` (lignes 767-863) qui détecte les clics et calcule les nouvelles positions en pourcentage. Le nettoyage des ressources est effectué à la fin du programme (lignes 1484-1509) avec des vérifications conditionnelles pour éviter les erreurs : `if (g.hasMenuBackground) UnloadTexture(g.menuBackground)`.
